Where students struggled

00:05:04 Warm-up question 2, what crashes_by_day > 2000 returns, was the one the room got wrong. The majority picked “just the days above 2,000” rather than seven TRUE/FALSE values. Fadel worked it from the named vector: the greater-than sign is a logical operator, and applied to a vector it returns TRUE or FALSE for every element, five TRUE for Monday through Friday and two FALSE for Saturday and Sunday, which were both under 2,000. He described it as the equivalent of a for loop that walks every element and asks whether the comparison holds. The option the room chose is what crashes_by_day[crashes_by_day > 2000] returns, and saying so pulled the central idea of Part 2 forward by half an hour.

00:02:23 The other two warm-up questions caused no trouble, and the explanations Fadel gave anyway are worth keeping. On question 1, which file to click before opening RStudio, eighteen of twenty-four votes went to business_intelligence.Rproj, which is the answer. Opening the project is not strictly required, but double-clicking the .Rproj guarantees the working directory starts where the folder is, which matters when the repo is opened on a different computer. Fadel said he had assumed on Monday that everyone’s layout was the M drive, then an ISA 401 folder, then the business_intelligence folder, and that it could just as easily be the M drive and then the folder directly. Either way the project opens RStudio inside business_intelligence. The README.md has no effect on RStudio at all, and .gitignore only tells Git which files and folders not to track, so neither starts a session. Question 3, typeof(c(2020, "Mon")), took seventeen of twenty-five votes for "character", which is right.

00:23:45 YAML indentation. Fadel mentioned that a student in one of the two sections had had the indentation of the output options wrong. The fix he demonstrated while typing the header: type the key and its colon first, then press Enter before typing the next key. RStudio indents the new line, and keeps indenting the lines that belong at that level.

00:35:29 After the job-ad debrief he asked for a show of hands, how many were close to at least some of the four answers, then turned to those who were not. He asked twice more, in different words, whether anyone wanted an explanation done differently, and repeated the standing rule that anyone who shows up should leave understanding everything he talked about.

00:50:00 In the predict activity, crashes_by_day[Sat] without quotes. The symptom is an object-not-found error rather than Saturday’s value; the cause is that unquoted, Sat reads as the name of an object in the environment, and no such object exists. Fadel had made the same point earlier while subsetting the vector by name, that the quotes are what separate a name from an object.

00:52:43 job["salary"]$max was the expression he expected to catch people, and he flagged that it is different from the one he had typed into the class markdown. The single bracket returns a list, and that outer list contains nothing called max. He said he believed it returned NULL rather than an error but was not certain off the top of his head, so he ran it. It returns NULL.

00:54:01 The autocomplete makes the reason visible, and he pointed at it: typing job["salary"]$ offers only salary, because the object at that point is a list of one whose single element is named salary. max is one level further down, which is why job["salary"]$salary$max is what reaches it.

01:03:37 The live debugging moment, and the one worth planning for. A student hit an object-not-found error; Fadel asked them to share their screen, then requested remote control to look. His two usual suspects are that the line creating the object was never run at all, or that Enter was pressed instead of Ctrl+Enter, which inserts a newline in the editor instead of sending the line to R. Here the object had simply never been created. This is the error he had flagged the previous class as one of the most frustrating things in R, because the messages are not plain about what went wrong. The fix was to run the line that creates it, and he thanked the student for sharing, because it produced the exact error he had described.

Questions from the room

00:07:44 A student had asked after the previous class what a vector actually is, and Fadel answered it during warm-up question 3. Think of it as a column of data in an Excel table, with the difference that a spreadsheet column will hold mixed things while R, like most other programming languages, generalises to the most general type that can store everything. In c(2020, "Mon") the number on its own is a double and "Mon" is character, so the only way to preserve both is to store the whole vector as text. Combining integers with doubles generalises to doubles the same way.

01:01:29 A student asked which package had just been installed. Tidyverse, which is a bundle rather than a single package: it brings dplyr, the source of glimpse(), and readr, the source of read_csv().

00:09:43 The session was framed around two errors he expects to cost students time, one in Part 1 and one in Part 3. His stated goal for the day was that the room leave knowing both and how to address them.

00:10:06 The Lego picture on the data frame slide carried the four vector types: logical as the grey and yellow tower, the output of something like crashes_by_day > 2000; categorical as a fixed set of labels, day of the week being Monday through Sunday and nothing else; numeric as a double or an integer; and character as the open one, where the number of possible values is effectively unlimited. He used the same picture again for the one-dimensional point, that pulling from a vector needs only one thing inside the brackets, a single number or a vector of numbers.

00:12:36 For the rule that all columns of a data frame must be the same length he gave a practical example that is not on the slide: web scraping, where two things come back at different lengths and the attempt to build a data frame fails, which is the signal that a cleaning step is needed first. He noted that Python errors the same way and for the same reason, because neither language knows how to line the rows up.

00:14:00 A matrix aside, not in the deck. Fadel raised matrices only because an AI assistant may well suggest one. A matrix looks like a data frame but can hold only one type, so combining numbers with characters turns the entire matrix to character. He drew a second contrast about named columns and hedged it in the same breath.

00:14:21 Two tibble-versus-data-frame differences he added for anyone who had not used a tibble: a tibble prints its size, its column names and its column types before any of the data, and extracting a one-by-one element gives a single element from a data frame but a one-by-one tibble from a tibble.

00:14:49 The four questions he put to any loaded data frame are how many rows, how many columns, what the columns are called, and what type each one is. nrow() and ncol() answer the first two, colnames() or names() the third. typeof() on a data frame is the odd one, reporting "list" rather than anything about a particular column, so asking about one column means writing something like crashes_df$day.

00:16:07 He then said he tends to ignore all of those and load dplyr for glimpse() instead, which gives the row and column counts, the names, the types and the first few values in one call. For anyone who has used R before it is similar to str() and just prints more readably; he left the choice open. He explained his colour convention in the same breath, since it shows up both on the slides and in his editor: mustard yellow is a package or library name, the bluish colour is a function name. He said he thought everyone in this section had used R before, which was not the case in his other section.

00:16:50 Lists were introduced as what usually comes back from an API, precisely because nothing in them has to match: a list can hold another list, a data frame, and vectors of different lengths at once. The slide’s example_list holds four elements, the integers 1, 2, 3, a single character "a", a logical vector of length 3, and a numeric vector of length 2.

00:18:20 The pepper shaker is the mental model he leaned on hardest, and the place he put the first of the day’s two frustrating errors. The shaker is the list and the packets are the elements. x[1] gets the first packet but leaves it in the container, so what comes back is still a list; x[[1]] hands over the packet; x[[1]][[1]] is the pepper. He tied it to why it matters: a function such as mean() takes a vector and not a list, so the container has to be opened before the function will accept what is inside. He came back to the shaker twice, at the job-ad debrief and again at the three-bracket summary table.

00:20:59 RStudio opened on whatever project was last used, which he pointed out was not the recommendation he had just made in warm-up question 1. The chunk, as it ended up:

Company is the second element, and the double bracket opens the container, so this is the string "Google". A single bracket here would have given a list of one instead.
2

3

4

00:35:51 The name he gave to what the activity had just done is subsetting: getting a subset of the data, and making sure that subset comes out in the format the next step needs. Part 2 then went back over it properly, since Part 1 had used subsetting without explaining it, and only for a list.

00:37:11 The second chunk is the vector subsetting section. The vector is real data, unique crashes in Cincinnati in 2025 summed by day of the week across the whole of last year, and it is named, so crashes_by_day[2] returns the second day, Tuesday, with its name attached, and crashes_by_day["Fri"] does the same for Friday. To pull more than one element the brackets need a vector, and when the wanted elements sit next to each other the colon does it.

#| eval: false
crashes_by_day = c(2020, 2241, 2327, 2285, 2380, 1866, 1664)
names(crashes_by_day) = c("Mon", "Tue", "Wed", "Thu",
                          "Fri", "Sat", "Sun")

1crashes_by_day[c("Wed","Fri")] # pulling elements by their name
2crashes_by_day[c(3,5)]

3crashes_by_day[1:5] # : only works for elements in a row [by their index]
4crashes_by_day[] # returns all the elements --> no diff than crashes_by_day
1
Two elements by name. The quotes are required: without them R reads Wed as the name of an object in the environment, and there is no such object.
2
The same two elements by position. Wednesday is the third day, Friday the fifth.
3
The colon only works when the elements are in a row, and it works on positions, not names.
4
Empty brackets return everything, which is no different from typing the object’s name.

00:43:25 No data frame chunk was typed; that material stayed on the slides. What Fadel added there is that crashes_df[["crashes"]] and crashes_df$crashes do the same thing, both pulling one column out as a vector, and that the two-dimensional form takes rows, a comma, then columns, where either side can be a single position, a range such as 1:2, a vector of positions such as c(1, 3), column names such as c("day", "crashes"), or a logical condition.

00:54:34 The third chunk is the CSV read. Three formats were promised for the day, CSV, Excel and JSON. read_csv() reads data on the machine and data on the web, as long as what it is pointed at is actually a CSV and not, say, a folder containing one; it works the same way as base R’s read.csv(), and Fadel said he prefers the underscore version because it guesses column types. Excel files have to be on the machine. JSON, the semi-structured format from the earlier class, can come from either. Only the CSV was reached.

00:55:47 The file is the Indeed job postings index for Ohio, served by FRED, with roughly five years of data. It is an index rather than a count: February 1, 2020 is set to 100, so a value above 100 means more job postings than there were on that date and a value below 100 means fewer.
